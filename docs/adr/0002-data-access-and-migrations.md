# ADR-0002: Data access, roles, row-level security and migrations

- Status: accepted
- Date: 2026-10-05
- Deciders: Viz (owner), build team
- Related: PRD invariants INV-01, INV-02, ARCH-01, RUN-01, 12.4; decisions D-09, D-10; B-002, B-008

## Context

Tenant isolation, an immutable balanced ledger and auditable changes are the core of the product. The data layer must make
the safe path the easy path and keep every security-relevant statement in reviewable SQL.

## Decision

1. **Access layer.** Synchronous SQLAlchemy 2.0 on psycopg 3, mostly explicit SQL via `text()` / Core. No lazy-loading ORM
   magic. The API sets request context per transaction and never connects as owner or superuser.
2. **Three database roles** (`infra/db/bootstrap_roles.sql`, idempotent):

   | Role | Purpose | Attributes |
   |---|---|---|
   | `dwaar_owner` | owns objects, runs migrations | NOSUPERUSER, NOBYPASSRLS |
   | `dwaar_app` | the API | NOSUPERUSER, NOBYPASSRLS, NOCREATEDB, no DDL |
   | `dwaar_worker` | background jobs | same restrictions, narrowly granted |

3. **Database provisioning** (`infra/db/create_database.sql`) is a superuser step: create the database owned by
   `dwaar_owner`, revoke everything from PUBLIC, allow CONNECT to the three roles, create the trusted extensions `pgcrypto`,
   `pg_trgm`, `btree_gist`, lock `CREATE` on schema `public` to the owner. `pgvector` is not created (B-004).
   Collation is `C` with `C.UTF-8` ctype (B-008).
4. **Row-level security.** Every society-owned table has `society_id uuid NOT NULL`, composite foreign keys that cannot
   cross societies, `ENABLE` and `FORCE ROW LEVEL SECURITY`, and a policy on
   `nullif(current_setting('app.society_id', true), '')::uuid`. Context is set with `set_config(name, value, true)`
   (transaction-local) for `app.society_id`, `app.person_id`, `app.actor_role`, `app.request_id`. **Missing context yields
   zero rows, never all rows.** RLS is defence in depth; the application permission service remains the primary gate.
5. **Migrations** are plain, ordered, checksummed SQL files in `services/api/migrations/`, applied by
   `dwaar_api.core.migrate.run_migrations(owner_dsn)` (table `schema_migrations`). A migration that creates a table also
   creates its RLS policy, constraints and grants. Expand-and-contract only; never destructive on posted data (RUN-01).
   Number ranges per area avoid collisions between parallel builders (0001-0099 platform core, 0100 org/identity, 0200
   devices/policy/visits, 0300 access events/edge sync, 0400 staff/parcels/shifts, 0500 helpdesk/ops/notices/community,
   0600 finance/ledger/payments, 0700 privacy/retention/AI audit, 0800+ M2+).
6. **Writes.** A domain mutation, its `audit_log` row and its `outbox` row commit in one transaction (PRD 12.4). Financial
   writes, approvals and command creation require an `Idempotency-Key` bound to actor, society, endpoint and request hash.
7. **Types.** UUIDv7 identifiers (`dwaar_common.ids`), money as `bigint` paise (`dwaar_common.money`, range-guarded to
   signed 64-bit), timestamps `timestamptz` stored in UTC.

## Consequences

- A forgotten `set_config` fails closed (empty results) rather than leaking another society's rows; tests prove it with the
  real restricted roles, not a superuser (see ADR-0003).
- Provisioning needs a superuser once per cluster; migrations do not. Managed Postgres providers must allow the three
  trusted extensions and custom roles.
- Hand-written SQL is slower to author than autogenerated migrations but is exactly what reviewers and auditors read.

## Alternatives considered

- Alembic autogenerate: hides grants/RLS in Python and tempts destructive diffs.
- A fully async stack: more moving parts, little benefit for this workload, harder transaction-scoped context handling.
- Schema-per-tenant: stronger isolation at the price of migration fan-out; revisit only if a single-schema RLS design
  fails the isolation acceptance tests.
